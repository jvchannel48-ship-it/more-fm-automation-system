# Deployment environment and admin persistence

`POSTGRES_URL` is the recommended production backend for the whole station. The application also accepts `POSTGRES_URL_NON_POOLING`, `DATABASE_URL`, or `SUPABASE_DB_URL`. PostgreSQL stores admin settings, the shared playback queue, listener counts, leases, and related state. Use a Supabase PostgreSQL connection URI—not the project URL or an API key—and apply the SQL migrations under `supabase/migrations/`.

For Render, add `POSTGRES_URL` to each required environment (Production, Preview, and/or Development) and redeploy. Copy the URI from the Supabase project's Database connection-string screen; keep its password private, never commit it or paste it into chat, and never expose it through a `NEXT_PUBLIC_*` variable. If using a pooler, select a Supabase mode supported by the deployed Node `pg` client.

## Admin-settings fallback without PostgreSQL

When no PostgreSQL URL is present, admin settings and the one-time settings-migration marker can instead be saved as private JSON objects in a dedicated `more-fm-settings` Supabase Storage bucket. The app creates the bucket if needed and verifies it is private before reading or writing. This fallback requires server-only `SUPABASE_URL` (or `NEXT_PUBLIC_SUPABASE_URL`) and `SUPABASE_SERVICE_ROLE_KEY` (or `SUPABASE_SECRET_KEY`). The settings object is stored under `app-state/station/settings.json`; do not put a service-role key in browser code or commit it.

The app also stores the station queue and no-repeat ledger in this private bucket when PostgreSQL is unavailable, so a single-instance restart can recover the daily played-song history. PostgreSQL remains strongly recommended for atomic queue leases, shared serverless coordination, and listener counts; without it, multiple simultaneous instances can still race. Configure `POSTGRES_URL` for a fully coordinated radio station. With neither durable backend configured, admin settings and queue state still work using process memory, but they are lost on server restart and are not shared between instances. The Admin Panel indicates when a save is temporary.

## Render persistent disk and RJ FM playlist

The included `render.yaml` mounts a persistent disk at `/var/data` and sets `MORE_FM_DATA_DIR=/var/data/more-fm`. The app checks that the configured directory is writable before advertising filesystem persistence. If Render returns `EACCES`, `EPERM`, or a read-only filesystem error, disk writes fall back to process memory; admin settings remain usable but are temporary until a durable backend is restored. Keep the Render disk attached and writable when using clear-build-cache deploys so the same-day no-repeat ledger survives the new build. On Sundays only, AutoDJ refreshes these playlists in the background every 60 seconds and can load up to 500 current entries, so newly added songs become eligible after the next queue refresh without a code change: Golden Sunday `PLZxu4AZwv5H0` from 4:00 AM through 11:59 AM, afternoon `PLWrP0D7Qkd-M` from 12:00 PM through 10:01 PM, and RJ FM `PLd469-e1TkbM` from 10:02 PM onward. The weekly starting offset changes while the shared Manila-day no-repeat ledger blocks repeats across all three windows.

The first persistent settings read fills any missing Tagalog-only, shuffle, and no-repeat preferences with their ON defaults while preserving every explicitly saved operator choice. On queue load, same-day persisted history is also added to the no-repeat blocklist, which prevents legacy songs from replaying after a version update or restart. Sunday programming is always a separate full-day Tagalog senior-classics rotation and does not add English songs, jingles, commercials, news, or DJ-mic clips between tracks. Admin changes are written to the active durable backend when configured; otherwise they remain process-local until restart.

See `.env.example` for variable names and placeholder shapes. It contains no usable credentials.
